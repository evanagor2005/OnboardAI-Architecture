## Domain model

**Confirmed relationships, before choosing tables:** One team may own many paths; each path belongs to one team and is independent of any employee. An invited employee is associated with one team. A team can have multiple appointed team admins, and one person can administer multiple teams; administration is a many-to-many relationship separate from employee team membership. Administering another team permits path management, review, and opening the path's linked source documents in the admin interface but does not add that team's paths to the admin's employee "My Paths" list. A path may be assigned to every member of its team or only to designated members; other members do not see that path. Every visible employee path is assigned for completion. The prototype does not have a separate required/optional setting. Each participating employee has their own progress and completion record against the shared team path. Completing a path must not delete the team-owned path. Path assignment does not restrict access to the underlying team documents; ordinary employee document access follows the document's team or shared classification.

**Confirmed path lifecycle:** An admin supplies a topic or keyword; the path generator creates and saves reusable path content and ordered steps at runtime. The admin reviews a new path before its first publication. When a source document changes in a way that affects a published path, a successfully regenerated revision goes live without another admin review. Existing active-path behavior still applies: a changed completed step prompts a revisit, while a changed future step updates without a notice. If refresh fails, keep the current path and show a freshness warning. Read-and-continue and question steps are in scope; question grading and answer storage still need design.

**Confirmed project relationship:** A Project is an assignable learning path that is not owned by a team. It presents the same kind of ordered steps as a team path. Projects form a shared catalog across team admins: an HR admin may assign a Project created by a Software admin to an HR employee. Projects and employees have a many-to-many assignment relationship: one Project may be assigned to multiple employees, and one employee may have multiple Projects at the same time. Each employee has independent progress on each assigned Project. Assignment authority still follows the existing employee-target rules: a team admin assigns employees on a team they administer; the Django superuser may assign employees on any team. The creating admin's team does not restrict who may assign an existing Project.

**Confirmed Project generation scope:** An admin generates a Project from a keyword and indexed documentation. An optional team filter searches that team's documents plus company-wide shared documents; with no filter, generation searches all indexed documents. The filter does not make the Project team-owned. Team admins may inspect cross-team source documents during Project creation and review under the prototype's non-confidential-document assumption. The saved Project should retain its generation keyword, optional filter, and source references so its basis can be inspected; exact columns and source-version links remain to design.

**Confirmed completion and Project publication lifecycle:** An admin reviews each newly generated Project before employees can see it. A later source-driven revision of a published Project publishes automatically after successful regeneration, without another admin review. When an employee completes a team path or Project, the shared definition and steps remain; that employee's step-progress state is deleted and a completion record linking the employee to the path or Project remains. If a relevant source changes afterward, a general warning that the completed path has changed is sufficient. Preserve enough path/Project-to-source provenance to find affected completers without retaining their completed-step history. Exact completion fields, provenance representation, and retention period remain open.

## Physical design

**Confirmed relational choice:** No cell in `team_paths`, `projects`, or an employee row holds a set of assignments. An all-team path uses team membership; a selected-members path uses a separate join table with one row per path–employee pair. Projects and employees use a separate many-to-many assignment table with one row per Project–employee relationship. Shared content is reused while employee progress is stored separately. The table names and remaining columns below are still proposals.

| Selected path audience | PostgreSQL | Separate join table chosen; `team_path_assignments` is a proposed name | One row per path ID and employee ID; unique pair | Used for selected-members paths; employee must belong to the path's team | Check whether a team member can see the path |

| Project | PostgreSQL | `projects` | Project ID; title/topic; generation keyword; optional source-team filter; reference to saved path content and supporting sources, exact representation open | No owning team or creator-team assignment restriction; initial publication requires admin review; later successful source-driven revisions publish automatically; one Project may have multiple assignees | Generate from all indexed documents or a team-plus-shared subset; find an employee's assigned Projects; let authorized admins select from the shared catalog |
| Project assignees | PostgreSQL | Separate assignment table chosen; `project_assignments` is a proposed name | One row per Project ID and employee ID; unique active pair proposed; assigning admin/time optional | Many-to-many; assignment authority follows team-admin appointments or superuser role | Check and list an employee's Project assignments |
| Project steps and progress | PostgreSQL | Shared or parallel step/progress tables to design | Ordered step identity and employee-specific progress | Same step experience as team paths; no assumption yet about shared physical tables | Show and resume an assigned Project |

The displayed step count can be derived from the published version's step rows. Storing a separate count on `team_paths` is an optional performance choice that would require keeping it synchronized. A stable way to match the same logical step across versions is still needed for revisit notices.

## Chosen approach and rationale

**Team design:** The team selected PostgreSQL with pgvector for the prototype's application records and vector search. This selects the DBMS and vector technology, not the final tables, indexes, or deployment layout. Team access classification applies to the whole document. Indexed sections or chunks derived from that document inherit its classification; different sections of one document will not be assigned different team access. Existing requirements also include company-wide shared documents. Whether one document may be associated with multiple teams remains open.

**Serious alternatives and tradeoffs:** The team compared PostgreSQL with pgvector against PostgreSQL plus Qdrant. The chosen approach has fewer data systems to operate and synchronize. A separate vector service remains a possible change if representative filtered retrieval tests show a concrete need.
